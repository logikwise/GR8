This is the current Studio refinement + OpenClaw/runtime integration pass. Treat it as a cleanup, stabilization, and architecture-strengthening phase.

Primary objectives:

1. Replace remaining local/semi-local OpenClaw runtime simulation with real OpenClaw execution wiring where possible by reusing preserved backend/runtime/adapter code
2. Consolidate broken GRACE routes so Dashboard / Org / related navigation no longer falls back into legacy or broken flows
3. Refine Studio so it behaves like a true node-based workspace, not a static diagram
4. Introduce or refine schema-first templates and persistent structures for Skills, Tools, and Workflow Blueprints
5. Eliminate in-memory-only storage for user-managed assets
6. Make Studio graph interaction calm, subtle, centered, and locally adjustable

Do NOT remove backend/runtime/orchestration/adapters.
Do NOT hardcode the product to OpenClaw only, even though OpenClaw is the first real provider.
Do NOT fake capabilities that are not actually supported through preserved runtime code.
Do NOT begin the full org/workspace tenancy refactor yet.

## Critical product rules

* Blueprint cannot run directly
* Only Instances can run
* Studio remains instance-centric
* Studio graph and flow remain instance-contained
* Workspace swarm remains outside Studio
* Provider health, run dispatch, event streaming, chat interaction, and agent discovery are separate capabilities and must be treated independently
* A healthy provider connection does not imply all runtime capabilities are available
* Skills, Tools, and Blueprints must be modeled as reusable library assets, not page-local objects
* No core user-managed GRACE asset may exist only in module memory if the user can create, edit, duplicate, delete, reopen, refresh, or deep-link to it

## Persistence rules (VERY IMPORTANT)

For this phase, legitimate persistence may be:

* existing backend persistence if available and practical
* otherwise a clearly isolated localStorage-backed service layer

But it must NOT be:

* module-level arrays
* temporary in-memory registries for user-managed assets
* page-local state as the source of truth

This applies to:

* Blueprints / Workflows
* Instances
* Runs
* Skills
* Tools
* Provider config
* Output/Library records if created by the user or produced by runs
* node positions/layout state where appropriate

If a user can:

* create it
* duplicate it
* edit it
* delete it
* refresh and expect it to still exist
* deep-link into it

then it must be persisted through a real service abstraction.

Use stable keys/versioned namespaces for local persistence where backend persistence is not yet wired, for example:

* grace.blueprints.v1
* grace.instances.v1
* grace.runs.v1
* grace.skills.v1
* grace.tools.v1
* grace.provider.v1
* grace.library.v1
* grace.layout.v1

## L. Studio graph and flow structural refinement

Refine Studio so it behaves like a true node-based workspace rather than a static strip on a large canvas.

### L1. Agents must be nodes, not a separate strip

Move the agent chips/badges out of the top strip and into the Studio graph as real nodes.

Requirements:

* primary agent = root node
* specialist agents = connected nodes in the graph
* chat remains conceptually tied to the primary/root agent
* do not keep agents as a separate strip above the workflow if they are part of the active instance structure

### L2. Shared node/edge model

Use one shared node/edge model for:

* agents
* steps
* skills
* tools
* outputs

Both Flow and Graph views should be based on this same underlying model.

### L3. Center workflow on canvas

The loaded workflow/instance must be centered on the available canvas.
Eliminate top-left bias and large empty dead space.

Requirements:

* centered initial layout
* fit-to-view behavior with padding
* few-node workflows should center visually
* switching between Flow and Graph should preserve positions where sensible
* do not leave the workflow pasted onto one corner of a giant empty canvas

### L4. Flow view behavior

Flow should remain sequence-first, but still be canvas-aware and centered.

Requirements:

* primary agent first
* steps in order
* attached skills/tools near the owning step
* outputs downstream
* horizontally organized by default on wide screens
* node cards clickable
* node cards draggable/repositionable where appropriate

### L5. Graph view behavior

Graph should use the same underlying node data, but allow more open positioning.

Requirements:

* draggable nodes
* clickable nodes
* repositionable workflow
* calmer, inspectable graph
* specialist/skill/tool/output relationships visible in context

### L6. Graph interaction physics tuning

Current issue:
Selecting a node causes the graph to reheat/reset too aggressively and all nodes snap/move with noticeable gravity. This feels unstable.

Update the graph so that:

1. Selecting a node does NOT restart or strongly re-run the full graph simulation
2. Node selection should only:

   * highlight the selected node
   * highlight connected edges/nodes
   * open the inspector
   * optionally apply a very subtle local emphasis
3. After the graph initially settles, the layout should enter a stable interaction mode:

   * low-motion
   * heavily damped
   * no global snapping on click
4. Users should be able to move individual nodes slightly by dragging them
5. Dragging one node should primarily affect that node, with at most subtle local easing on nearby connected nodes
6. Releasing a dragged node should allow it to settle softly nearby, not trigger a full-layout reset
7. Keep node positions persistent for the current instance/view
8. Do not recenter or re-fit the entire graph on every selection
9. Only use stronger layout/force behavior on:

   * first load
   * switching into graph view
   * loading a different instance/blueprint
   * adding/removing nodes

Desired feel:

* calm
* subtle
* inspectable
* locally adjustable
* not a constantly reflowing force simulation

Think:

* calm constellation
  not:
* shaken snow globe

### L7. Inspector integration

Clicking nodes in both Flow and Graph should open the appropriate detail inspector.
Reuse existing StepInspector or evolve it into a broader node inspector where appropriate.
Do not duplicate inspector logic unnecessarily.
